## Reproduce Device Checks

Run from `flutter/`, with a disposable device selected explicitly:

```sh
flutter test integration_test/downloads_test.dart -d <device-id>
flutter test integration_test/download_notice_test.dart -d <device-id>
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/update_notice_test.dart -d <device-id>
flutter test integration_test/playback_test.dart -d <device-id> \
  --dart-define=PLAYBACK_FIXTURE_BASE64=<base64-of-a-small-H264-mp4>
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/application_test.dart -d <device-id> \
  --dart-define=LIVE_APPLICATION_SMOKE=true
python3 tool/verify_predictive_back.py --device <disposable-android-id>
ANDROID_SERIAL=<disposable-android-id> ./android/gradlew -p android \
  :app:connectedDebugAndroidTest --no-daemon
```

The live journey is opt-in and requires current upstream availability. Its screenshot driver writes to ignored `build/qa/`; the production-composition portion uses native plugins rather than substituting fake backends. The predictive-back runner requires gesture navigation, `flutter` on PATH and either `adb` on PATH or `ANDROID_HOME`/`ANDROID_SDK_ROOT`. It injects touchscreen edge drags on the explicit emulator serial, waits for the application's gesture-progress assertion and screenshot, then reverses or releases the drag. It does not synthesize Flutter back-channel messages. The appended download-card screenshots use explicitly marked presentation-only fixtures. Dart unit/controller/widget tests separately use controlled HTTP services, disposable SQLite and fake platform boundaries. Do not treat those tests as device evidence.
